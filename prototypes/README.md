# prototypes/

答えが紙の上では出ない問いを、動かして確かめるための場所。**製品コードではない。**

`src/` と違うのは目的だけで、扱いは同じ——`tsconfig.json` の `include` に入っていて、
`npm run typecheck` と `npm run lint`（関数の大きさの3つの上限を含む）が効く。
効いていないのは**カバレッジだけ**で、`vitest.config.ts` の `coverage.include` が
`src/**/*.ts` なので、ここにテストの無いコードを置いても閾値は動かない。

そのぶん、**ここで分かったことは `src/` に持っていくときに書き直される前提**で置くこと。
プロトタイプが実装になったら、このディレクトリからは消す。

## terrain — 船橋から見た陸

```
npm run dev
open http://localhost:5173/prototypes/terrain/index.html
```

参照事案（周防灘、`examples/suo-nada-2025-11-27.voyage.json` の origin）に立って、
地理院の標高タイルで陸を出し、地球の曲率を入れた船橋視点。開始時刻は接触の瞬間
（2025-11-27 18:13:30 JST）で、そこから時計を回すと昼になる。

| 操作 | |
|---|---|
| ドラッグ | 見回す（離すと 250 ms 後にタイルを取りに行く） |
| `,` `.` | 時計を ∓1 時間 |
| `<` `>` | 時計を ∓10 分 |
| `R` | 接触の瞬間に戻す |
| `C` | 曲率 on / off |
| `W` | ワイヤフレーム |
| ↑ ↓ | 眼高 5〜60 m |

左上の数字が答えそのもの: 時刻と太陽・月の位置、取得したタイル数、そのうち陸だったもの、
転送量、水平線距離、各距離で水平線に隠れる高さ。

**明るさは切り替えではなく時計から出している。** `lighting.ts` が `core/conditions.ts` を
読み、太陽の実際の高度と方位で照らす——これは `CLAUDE.md` が書いている
「`render/` は `environment` を読まず `Conditions` を読む」の実装例でもある。
方位と高度は計算値、**色と強度の値そのものは手で作ったランプで、放射量からは出していない**。
雲は入っていないので、すべて晴天時の上限。

物理との突き合わせ（この事案、緯度 33.905、2025-11-27）:

| 時刻 (JST) | 太陽高度 | 方位 | sunLevel |
|---|---:|---:|---|
| 11:53:30 | 34.9° | 178 | day |
| 16:33:30 | 4.9° | 240 | day |
| 18:13:30（接触） | −14.2° | 254 | astronomical-twilight |

南中高度の理論値は 90 − \|33.905 − (−21.1)\| = 35.0°。方位 178 なので南中の 2° 手前で、
一致している。接触時は既に航海薄明（−12°）を過ぎていて、`CLAUDE.md` の
「接触の 11 分前に航海薄明が終わる」と符合する。**そしてこのとき月は高度 40.7°・輝面 41%
で出ている**——夜の事案として扱う前に、月明かりがあった事実のほうが先に効く。

赤い柱は計測器で、風景ではない。**500 m 高・400 m 幅を 20 / 40 / 60 / 80 / 100 km に、
方位を 8° ずつずらして**置いてある。`C` で切り替えると、隠れる量が左上の数字どおりに
変わることを目で確認できる。実測との突き合わせ:

| 距離 | 隠れる高さ | 見える角度 (曲率 off → on) | 実測 (off → on) |
|---:|---:|---|---|
| 20 km | 1 m | 1.432° → 1.430° | 1.382° → 1.382° |
| 40 km | 36 m | 0.716° → 0.665° | 0.679° → 0.631° |
| 60 km | 126 m | 0.477° → 0.358° | 0.437° → 0.315° |

差（＝曲率がやった仕事）は 3 桁目まで一致する。絶対値が 0.04° ほど小さいのは、
柱の足元が水平線と重なって数え落ちるため。

### ここで確かめたこと

- `render/tiles.ts` と `core/geodesy.ts` は**そのまま使える**。標高タイルの配置は
  淡色地図とまったく同じ「タイルごとに四隅を `toLocalPosition`」で足りる
- 海はタイルが無い（404）。参照事案の周囲 46 km で、要求 149 枚に対し陸は 70 枚
- 曲率は頂点シェーダの1行で足りる。ただし**水面も一緒に曲げないと水平線が出ない**
  （`water.ts` が眼を中心にした等比リングの円盤にしてある理由）
- 1 フレーム 11.5 ms（中央値、3708 × 2268、`readPixels` でパイプラインを同期させた実測）

転送量は**向いている方位で決まる**。同じ 90° の楔で:

| 見る方向 | 要求 | 陸 | 転送量 |
|---|---:|---:|---:|
| 西（外洋） | 54 | 20 | 949 kB |
| 北（山口県の海岸） | 89 | 46 | 3.09 MB |
| 北、遠距離リングを z11 → z10 | 74 | 33 | 1.86 MB |

遠距離リングを1段落とすと 40% 減る。z10 は 127 m/px で、40 km では画面 1 px が 55 m
なので粗いほうに 2 倍強。**稜線がそれで壊れるかどうかは見て決める話**なので、
既定は z11 のままにしてある（`RINGS` の1行）。

### まだやっていないこと

- **タイル境界の継ぎ目。** 隣り合うタイルの端の頂点が、別々の画素を読んでいる。
  ズームが粗いほど段差が出る。1 px 重ねて取るか、端だけ平均する
- **間引きが最近傍。** 標本の間にある尖った山頂が消える。最大値フィルタが素直
- **デコードがメインスレッド。** 間引き後は 5 ms/枚なので今は耐えているが、
  到着が固まるとフレームを落とす。Worker に出す
- **灯が無い。** 夜の陸はほぼ真っ黒で、これは正しい。夜の事案で読むべきものは
  航路標識で、それはタイルではなくシナリオに入るデータ
- **日本の外。** 標高タイルは日本で止まる

昼にしたときだけ出る問題:

- **陸にテクスチャが無い。** 標高だけなので、日中は単色のマット。稜線は読めるが、
  「どこの海岸か」は読めない。写真タイル（`seamlessphoto`）を貼る手はあるが、
  当日の見え方ではないものを貼ることになるうえ、航空写真は淡色地図と利用条件が別
- **リングの継ぎ目。** z14 と z13 のタイルが隣り合うところで高さが合わず、割れる。
  夜の黒いシルエットでは見えないが、昼は見える
- **影が無い。** 太陽の向きで陰影は付くが、山が山に落とす影は出していない。
  夕方の低い太陽ほど効くところ
- **空が単色。** グラデーションも太陽の円盤も無い
