# Blender 書き出し（動きを glTF アニメーションで出す）

## 何を

シナリオの**動き**を glTF アニメーションとして書き出す。位置・船首方位・2つのカメラ・時刻を
チャンネルに持たせ、Blender（や glTF を読む何か）が同じ動きをレンダリングできる状態にする。

`render/record.ts` は「ブラウザが描いた画」を捕まえるもので、動きそのものは外に出ない。

## なぜ

**1つの入力から2つの出力。** 検証用のリアルタイム再生と、発表用の高品位映像を、同じ
`.voyage.json` から出す。

映像を別作業で作ると必ずズレる。再生は「17:44 に 12 m」と言い、映像はアニメータが置いた
キーフレームの通りに動き、**誰も突き合わせない**。このレポは小さいところで既にこれを拒否して
いて、`ui/panels.ts` が `render/player.ts` と同じ入力から文を組み立てるのは、
`plans/done/antenna-offset-6.md` のクロスレビュー指摘 6 件が全部「パネルが絵より強い主張を
している」だったから。手で作った映像は、同じ失敗を出力全体の規模でやることになる。

**なぜ glTF で、Blender の Python スクリプトではないか。** glTF の規約が Y-up・−Z forward で、
`render/coords.ts` が既に出している形と同じ。`.py` を吐く経路は軸変換をもう一組ゼロから書くこと
になり、そこで符号を1つ間違えても長いあいだ「それらしく」見える——`coords.ts` が「世界の軸を
決める唯一の場所」と書いている理由そのもの。glTF なら Blender 以外にも開く。

### 素直な実装だと何が間違うか

1. **Blender が Z-up だからと、書き出し器で Z-up に変換する。** やってはいけない。glTF の規約は
   Y-up で、Blender の glTF インポータが読み込み時に変換する。親切のつもりで先に回すと二重に
   かかって**北と南が入れ替わる**。書き出すのは `coords.ts` の座標系のまま
2. **回転をオイラー角の数値で持ち回る。** `headingToRotationY` は `-heading` rad（コンパスは
   時計回り、Y-up 右手系は反時計回り）。glTF のチャンネルは quaternion なので、書き出す前に
   quaternion にする。数値のまま渡して Blender 側で XYZ オイラーとして読むと軸順でずれる
3. **書き出し器がアンテナ補正を自前で計算する。** `render/player.ts` の `placementOf()` は
   「HDG も COG も無い標本には補正を当てない」という判断込みで、これを再実装すると映像だけ
   21 m ずれる（`test/examples.spec.ts` が符号を固定している量そのもの）。**同じ関数を通す**
4. **平面図のズームをカメラの高さで表現する。** `frameOverheadCamera` は毎フレーム
   left/right/top/bottom を書き換えている。正射投影なので**カメラを上げ下げしても画は変わらない**。
   Blender 側は `ortho_scale` を打つ。アスペクトは出力解像度が持つ
5. **クリップ距離を既定のままにする。** Blender のカメラ既定 `clip_end` は **100 m**。
   `makeOverheadCamera` は 60000、`makeBridgeCamera` は 80000 を使っている。既定のままだと
   何も映らない
6. **航海灯を光源として置き直す。** 水平 112.5° / 225° / 135° の扇形（垂直は無制限）は spot の
   円錐では作れない。灯火は光源ではなく**見えるかどうかの判定**なので、`visibleLights()` の結果を
   フレームごとに焼いて emissive の on/off で出す。光源に化かすと、判定と絵が別々の答えを持つ
7. **地図タイルを埋め込む。** 地理院タイルは実行時取得・出典明示なら申請不要だが、glTF に焼けば
   複製になって扱いが変わる（`src/render/basemap.ts` 冒頭）。書き出すのは**四隅の緯度経度と
   URL テンプレート**まで
8. **出所（derivation）を落とす。** 実線／破線を映像側に持ち込めないなら、その映像は Blender 単体で
   作ったものと同じ強さしかない。**それをやらないためにこの issue がある**ので、最初の版から入れる
9. **時刻と出典を映像の外に置く。** `render/overlay.ts` が canvas の中に描いているのは、録画が
   `captureStream()` で canvas の外の DOM が1フレームも映らないから。Blender でも同じものが
   コンポジット側に要る

## 着手条件

**`plans/ship-motion-model.md`（一次遅れ）が入るまで、書き出したもので発表しない。**
`sampleAt()` は今も標本間を直線で結んでいて、船が横滑りして見える。それを映画品質で描くと、
**発明した部分が画面で一番きれいなもの**になる。垂直寸法も #8 に出典が入るまで同じ状態。

書き出し器そのものは先に書いてよい。

## どのファイル

- 新規 `src/export/gltf.ts` — サンプル列 → glTF JSON（`src/extract/` の対）
- 新規 `scripts/export-gltf.mjs` — CLI。`scripts/build-single.mjs` と同じ形で `dist/` に出す
- `src/render/player.ts` — `placementOf()` を export して書き出し器と共有する
- `src/render/cameras.ts` — 画角の決め方（`frameOverheadCamera` の extent）を再生と共有する
- 新規 `test/export-gltf.spec.ts` — 罠 1・2・3 にそれぞれ 1 本。特に「北が北のまま出る」
- `docs/` — Blender 側の読み込み手順とコンポジットの前提

## 未解決

- **何を書き出すか。** 船体とカメラだけか、航跡線と地図の板も含めるか。地図は罠 7 があるので
  板とタイル URL だけ出して素材は各自が取る形になる
- **船体形状。** Blender 側で差し替える前提にするなら、書き出すのは変換行列だけでよい。#8 と絡む
  ——借りたモデルを縮尺して合わせるのは別の船の絵、という `render/hull.ts` の判断は書き出し先でも
  効かせる必要がある
- **時間の写像。** 再生は 20 倍速。映像の fps とフレーム番号への写像を1か所に持つ。固定 fps で
  丸めると標本がフレーム境界からずれる
- **破線をどう出すか。** glTF に線種は無い。マテリアルで抜くか、ジオメトリを刻むか。罠 8 の実体は
  ここ
- **静止画を含めるか。** 1枚絵（報告書の図）が要るなら、アニメーションではなく1フレームの
  書き出しになる
