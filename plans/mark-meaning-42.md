# 標識の意味を1つ持ち、色・頭標・灯質を生成する（issue #42）

## 何を

IALA の標識は**同じ1つの事実を3回言う**。北方位標は「黒上黄下」「上向きの円錐2つ」「Q」で、
どれも「北」と言っている。孤立障害標は「黒に赤の横帯」「球2つ」「Fl(2)」。

**その冗長性が設計そのもの**——縞は昼のため、頭標は色が読みにくいときのため、灯質は夜のため。
1つを失っても標識が identify できるように3回言っている。

だから**フォーマットは事実のほうを持ち、3つを生成する**。3つを独立したフィールドで持たせると、
「黒黄の縞・球2つ・Fl(2)」という**誰にも識別できないキメラ**が、何の文句も出ずに描ける。
このレポが繰り返し直しているのと同じ形が1階層内側にある: 1つの問いに3つが答えていて、
互いに食い違える。

上書きは可能にする（実物は逸脱するし、目撃者は3つのうち1つしか見ていないことがある）。
ただし既定は生成で、**パネルがどれがファイル由来かを書く**。

## 素直な実装だと間違うところ

### 1. 地域を座標から推測しない

B 地域は南北アメリカ・日本・韓国・フィリピン。境界は地図であって計算式ではないので、
**緯度経度からは導けない**。記載が無ければ側方標識の色は**生成しない**——
#40 の振れ回り円・#41 の灯火と同じ3値で、「記載なし／生成できない」と「無彩色」は別物。
方位標識・孤立障害・安全水域・特殊は地域に依らないので、地域が無くても生成できる。

### 2. 色は1色ではない

いまの `colour` は単色5つで、スキーマ自身が「縞と帯は表現できない」と書いている。
**それは体系のほぼ全部**（方位標識は全部帯、安全水域は縦縞、孤立障害は帯）。
`colour` を `pattern` に置き換える——単色は「1色の pattern」。
2つ並べると、**1つの問いに2つが答える**構造をこの変更自身が作ってしまう。

### 3. 3つのうち「ファイルが言ったもの」を上書きで消さない

生成は既定であって強制ではない。ファイルが色を書いていれば色はファイルのもの、
灯質を書いていれば灯質はファイルのもの。**パネルが3つそれぞれについて出所を書く。**
（#41 の「記載なし／読めない／読めた」と同じ形で、今度は3軸ある。）

### 4. 灯質の候補が複数あるものを黙って1つに決めない

北方位標は「VQ **または** Q」で、どちらも正しい。安全水域は4通り。
**選んだことをパネルが書く**——選択自体は避けられない（何かを描く必要がある）が、
黙って選ぶと「報告書がそう言っている」に見える。

### 5. 灯標の構造は意味ではない

灯標の形（塔・櫓・柱・杭）は工学であって、何も意味しない。格子櫓の北方位標も
コンクリート柱の北方位標もある。**意味の軸とは独立**なので、別のフィールドにする。
浮標側の同じ軸が IALA の形状（can / cone / sphere）で、あちらは**部分的に意味**を持つ
（缶は左舷、円錐は右舷）——#40 が種別を分けたのはこの2つが別物だから。

## どのファイル

- 新規 `src/actors/mark/buoyage.ts` — 意味 → 見え方（pattern・頭標・灯質の候補・形状の候補）。
  `core/light-character.ts` に依存してよい（actors → core は正しい向き）
- `spec/voyage.schema.json`, `src/core/types.ts` — `marks[].purpose`、`marks[].pattern`
  （`colour` を置換）、`marks[].construction`（灯標のみ）、`meta.buoyageRegion`
- `src/render/mark.ts` — 帯と縦縞を**ジオメトリで**描く（テクスチャにすると canvas が要り、
  Node のテストが DOM を必要とする）。頭標（円錐2つの4通り・球・缶・X・十字）。灯標の構造
- `src/render/player.ts` — ファイルが灯質を書いていなければ意味から生成したものを使う
- `src/ui/panels.ts` — 3軸それぞれの出所
- `docs/domain-notes.md` — R1001 の表と、この5つの罠

## この変更に入れないもの

- **航路の向き（conventional direction of buoyage）**。側方標識の左右はそれが決めるが、
  海図に書かれるもので、このフォーマットはまだ持っていない。標識の意味だけを持つ
- **AIS AtoN と Racon**（R1001 が各表に挙げている補助手段）。描くものが無い
- **番号・文字**（`2.4.1.2` の numbering/lettering）。#42 の主題ではない
- **水面への映り込み**（#39）と**光達距離**——#41 から持ち越しのまま

## 実装して分かったこと

**出所は3値では足りず、4値だった。** 規格が値を「一意に決める」場合と「候補を絞るだけ」の
場合が混ざっている——方位標識の色は黒上黄下しかないが、胴体は柱でも棒でもよく R1001 は
決めていない。柱を「意味から」と報告するのは、**この工具の選択を IALA の権威の後ろに隠す**
ことになる。発明した色を記載と呼ぶのと同じ overclaim が1段内側に入っただけ。

| 出所 | 例 |
|---|---|
| 記載 | ファイルが `pattern` を書いた |
| 意味が一意に決めた | 方位標識の色、優先航路標識の `Fl(2+1)` |
| **意味が許す複数から選んだ** | 方位標識の胴体（柱 or 棒）、安全水域の灯質（4通り） |
| 何も無いので選んだ | purpose も pattern も無い標識 |

**`purpose` から形を生成すると、「ファイルの `shape` を読む」既存コードが古い前提のまま残る。**
灯火の位置がそれで、purpose から球形になる安全水域標識の灯が空中に浮いていた
（codex iter-1）。**生成を足したら、その値を読んでいた場所を全部探すこと。**

**語彙を足したら、語彙が無いと言っている文を探すこと。** 灯標の構造を追加したのに、
パネルの注記は「このフォーマットには塔・櫓・柱・杭の語彙が無いので画面の形はこの工具のもの」
と言い続けていて、記載された `lattice` のセルと直下の注記が矛盾していた（codex iter-3）。

**規格が「あるなら」と書いている欄は、あったかどうかを決めていない。** R1001 の頭標欄は
すべて "Topmark (if any)" で、気象や氷で頭標を付けない判断もあると本文に書いてある。
つまり**意味は「頭標が何であるか」を決めるが、「頭標があったか」は決めない**。描くのは
避けられない（昼間の識別はそれで読む）が、描いた判断はこの工具のもので、4値目に入る
（codex iter-4）。ファイルが `topmark: false` と言えることも必要——「無かった」は
欠落ではなく事実。

**「記載された不在」は「分からない」ではない。** `topmark: false` と、何も書かれていない
ファイルは、**絵では同じ**（頭標が無い）が**ページでは別**でなければならない。前者は出典が
言った事実で、後者は出典の限界。畳むと出典が言った唯一のことが消える（codex iter-5）。
#40 の振れ回り円で「灯標は円が無い / 大きさが不明 / 数値」を3つに分けたのと同じ形が、
真偽値のフィールドにも現れる。
