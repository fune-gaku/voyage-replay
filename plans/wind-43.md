# 風を持てるようにする（issue #43）

## 何を

`environment.wind` を足し、いま塞いであるだけの仮定を消す。`core/seaway.ts` が風を使い、
パネルがどこから来た値かを書く。

## 素直な実装だと間違うところ

### 1. 風が決めるのは風浪であって「海」ではない

遠方の低気圧から来るうねりは別方向から走る。それが普通で、実海面が混沌として見える理由。

**優先順位は3段**にする。`waves.fromDegreesTrue`（記載）＞ 風向から導出 ＞ 名前の付いた仮定。
パネルはどの段だったかを書く。風を足しても仮定が消えるのではなく、**段が1つ増えて仮定が
後退する**だけ。そう書く。

### 2. 完全発達には吹送距離と継続時間の両方が要る

`Hs = 0.21 U²/g` は完全発達の関係で、風が上がっている最中の海はそれより小さい。
つまり**風は波高の上限であって波高ではない**。逆向きの誤りは無い——記載の海が風の支える
上限より大きければ、うねりか転記ミス。

**だから突き合わせは非対称。** `statedLightAgrees` が「比較できる軸でだけ比較する」のと同じで、
「海 ≫ 風の上限」だけを報告し、「海 ≪ 風の上限」は普通のこととして黙る。

### 3. ビューフォートは階級であって数値ではない

BF5 は 17〜21 kn。海面状態を中央値で潰さなかったのと同じ理由で潰さない。

**そこで役割を分ける。** 風速が記載されていれば周期の導出に使う。**風力階級しか無ければ
範囲として運び、突き合わせと風向にだけ使う**——単一の周期を出すために中央値を発明しない。
風力階級の主な価値は突き合わせと風向のほうにあるので、これで失うものは小さい。

### 4. 周期の導出は「順方向」になるが、バイアスの向きは変わらない

いまの `assumedPeakPeriodSeconds` は Hs → U → Tp と PM を逆に回している。風速があれば
U → Tp で済む。ただし**どちらも完全発達を仮定するので、内海で長く出るバイアスはそのまま**。
消えるのは往復であって偏りではない。そう書く。

## どのファイル

- `spec/voyage.schema.json`, `src/core/types.ts` — `environment.wind`（`derivation` 必須）
- `src/core/seaway.ts` — ビューフォート換算（範囲）、風速からの周期、風向の優先順位、
  完全発達の上限と突き合わせ
- `src/core/conditions.ts` — `Conditions` に風を載せる
- `src/ui/panels.ts` — 風の行、波向がどの段から来たか、突き合わせの結果
- テスト — ビューフォートは公表値に、PM は公表の係数に、優先順位と非対称な突き合わせを固定

## この変更に入れないもの

- **吹送距離の計算。** 風向と海岸線から求まり、地形タイルは既にある。既知バイアスを注記から
  計算に変える話で、それ自体が独立している
- **風浪＋うねりの2成分スペクトル。** 実海面はそうだが、`seaway.ts` の全体を触る
- **リーウェイ（風圧流）。** 船の話であって海の話ではない
