# 天頂から水平までの自由視点を1本載せる（issue #65）

## 何を

`ViewSelection` に 4 つ目——ではなく **3 つ目の「相対的な眼」**を足す。

```ts
| { kind: "orbit"; azimuthDegrees: number; elevationDegrees: number; distanceMetres: number }
```

そして画の下のコントロールを、**海図のものと再生のものに分ける**。

## なぜ

#63 は「どういう画か」と「眼はどこか」を割り、`render/cameras.ts` に自由カメラが生えた。
**ページからは選べない。** `{ kind: "free" }` の消費者は `test/player.spec.ts` だけで、
UI にあるのは Chart と船ごとの bridge。割ったことを絵で確かめる者がいない状態で、
これは #63 の plan 自身が「割っただけで消費者を作らないと、割り方が正しいか誰も検証しない」と
書いたその失敗。

## なぜ `free` をそのまま UI に出さないか

**`free` は絶対的な眼**（位置・船首方位・眼高）で、**軌道は相対的な眼**（何のまわりを回るか）。
そして「何のまわり」＝行動の中心は、既に `Replay.frameOverhead()` の中にある。

`frameOverhead()` を UI から呼ぶことはできない。**あれは海図のもので、海図のものであり続ける
必要がある**——地図タイルの取得範囲も決めているので、ワールドの視点から呼ぶと
**誰も描いていない矩形の地図を取りに行く**（#63 で明記した）。

かといって UI 側で中心を計算し直すと、「行動の中心はどこか」に**2 つの答え**ができる。
このレポが繰り返し踏んでいる形。

だから中心の計算を `frameOverhead()` から `centreOfAction()` に括り出し、
**海図と軌道が同じ 1 つの答えを使う**。地図の取得は括り出さない（海図だけのもの）。

`bridge` が既に同じ形をしている——**船に相対的な眼**で、player が解決している。
軌道は「行動に相対的」なだけで、新しい種類の問題ではない。

## 素直な実装だと何が間違うか

- **UI で `free` を組み立てて毎フレーム `setView` する。** 上記のとおり中心が二重定義になる。
  さらに `setView` は視点の変更であってフレームの前進ではないので、毎フレーム呼ぶと
  「視点が変わった」扱いの副作用（`fixedCentre` のリセット等）が毎フレーム走る
- **仰角 90°（天頂）で `placeFreeCamera` が退化する。** YXZ オイラーで pitch −90° を作ると
  ロールが方位に吸収されるので、**方位を回すと画が回る**。これは軌道カメラとしては正しい
  挙動（天頂で方位を回す＝海図を回す）だが、`up` の取り方次第で反転しうるので、
  真上ちょうどではなく **89.9° で止める**。それでも「ほぼ天頂」は満たす
- **仰角 0° で眼が水面下に入る。** 距離 × sin(仰角) が眼高なので、0° は眼高 0 m ＝
  水面そのもの。**水面のディスクは眼を中心に置かれる**（`render/water.ts`）ので、
  眼高 0 だと水面が視線と同一平面になり、水平線が出ない。**下限を 0.5°** にし、
  さらに眼高に床（2 m）を持たせる
- **`eyeFor()` が「眼が無い」を bridge の意味で返している。** 現状 `null` は
  「そのショットに自船の航跡が届いていない」で、`activeCamera` はそれを見て
  **俯瞰カメラに落ちる**。軌道視点で同じ経路に落ちると、海図を描いていないのに
  海図のカメラが選ばれる（`Picture` は world のまま）ので、**曲がった地球に平行投影**という
  誰も設計していない画になる。軌道は常に眼を持てる（中心が無ければ原点）ので、
  `null` を返さない
- **`facing()` が `view.kind !== "free"` で 0 を返す。** 軌道を足して忘れると、
  **カメラは正しい位置に置かれて水平を向く**——動くし、それらしく見えるし、間違っている
- **海図専用のコントロールを `disabled` のまま置いておく。** 「効かないボタン」は
  「壊れたボタン」に見える。**隠す**

## どのファイルを触るか

| ファイル | 何を |

| `test/transport.spec.ts` | モードごとのドラッグ／ホイールの行き先、海図専用の表示 |

## 未解決の問い

- **軌道視点の「スケール」をどう述べるか。** 海図はメニューが縮尺を名乗る。透視投影に
  一様な縮尺は無いので、名乗れるのは**中心までの距離**しかない。時計と同じく canvas の
  中に出すのが筋だが、`overlay.ts` の caption は 4 隅で埋まりつつある。この PR では出さず、
  出していないことを issue に残す
- **船橋視点で見回せるようにするか。** `placeBridgeCamera` が船首方位を向き水平を保つのは
  **主張**（窓が向くのは針路、当直者は水平線を見ている）。マウスで動かせるようにするのは
  別の判断で、ここには入れない
- **軌道の中心を船に固定できるようにするか。** いまは行動の中心（両船の中点）だけ。
  1 隻を追う軌道は「その船の船橋ではないが、その船のもの」という 3 つ目の相対で、
  要るかどうかは使ってから決める

## 追記: 相対をやめた（issue #67）

上で「**軌道は相対的な眼**であるべき」と書き、`free`（絶対）を UI に出さない理由にした。
**前提は正しく、結論が間違っていた。**

「何マイルも走る事案では、metre を保つ眼は置いていかれる」——これが相対にした理由だが、
何マイルも走る事案こそ**固定点が要る**。問いは「2 隻がある場所に対してどう動いたか」だから。

そして相対だと、**読んでいる最中に視点が動く**。角度も距離も「どこから測ったか」に乗るので、
中心が漂えば、読者が触っていないのに幾何が変わる。使ってみてすぐ出た。

いま `orbit` は**絶対**（centre・方位・仰角・距離）。海図をクリックして場所を選び、
そこに立ち続ける。**残ったのは「行動の中心はどこか」の答えが 1 つであること**——
`Replay.actionCentre` が唯一の答えで、海の視点は開くときと Recentre のときに**一度聞く**。
一度聞くのは 2 つ目の答えではない。
